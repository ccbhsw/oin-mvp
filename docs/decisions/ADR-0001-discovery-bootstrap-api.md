# ADR-0001：采用签名静态 Bootstrap API 作为 Discovery 的可逆起点

- **状态：** 已接受（原型）
- **日期：** 2026-08-21
- **决策范围：** 节点发现的最小可运行接口；不改变身份锚定、签名算法、数据删除机制或治理章程。

## 背景

OIN 已有可验证的 Observation、复制和离线验证闭环，但节点复制仍依赖人工提供 `peer_url`。仓库已有签名 `OperatorDescriptor` 与 `BootstrapRegistry`，却未暴露给运行中的节点。因此新参与者无法从节点取得可验证的候选 Operator 记录。

## 决策

节点提供两个只读端点：`GET /v1/discovery/descriptor` 公开自身的短期签名描述符，`GET /v1/discovery/peers` 公开自身加上本地静态 Bootstrap Bundle 中的有效描述符。节点不会抓取远程描述符，不会自动导入网络数据，不会根据描述符自动复制。

描述符只从运营者明确声明的 `OIN_DISCOVERY_ENDPOINTS` 构建；缺失配置时以 `503` 失败。Bundle 在读取与解析前受到 256 KiB、128 条描述符的容量限制。所有候选描述符均须通过签名验证、确定性 `operator_id` 检查和有效期过滤。每当本地 Bundle 哈希发生变化，节点将追加一条本地 Ed25519 签名、哈希链式审计记录，包含 Bundle SHA-256、接纳/拒绝描述符数和活跃记录数；同一 Bundle 不会因每次只读请求重复写入。

## 后果

该方案足以让多个独立镜像或人工导入路径传播可验签的节点元数据，并让本地运营者事后核验自身配置 Bundle 的来源哈希和解析结果；但仍有 Bootstrap 入口集中、Sybil、端点可用性、真实性、地域独立性和合规状态未知等限制。客户端必须继续显式选择复制对象，不能将 Discovery 响应理解为 OIN 的信任背书。

## 被拒绝的替代方案

| 方案 | 本阶段不采用的原因 |
| --- | --- |
| 立即引入全局 DHT | 不能消除初始入口，且会在未完成 Sybil、隐私和流量威胁建模时扩大攻击面。 |
| 唯一官方目录 | 形成单点故障和事实中心化的默认入口。 |
| 自动拉取和复制发现到的节点 | 将元数据发现与存储承诺混合，会放大 SSRF、带宽与法律风险。 |
| 无签名 JSON peers 列表 | 无法独立证明描述符与其声明公钥相符，容易被中间人或镜像篡改。 |

## 重新评估触发条件

当至少两个独立 Operator 能互换 Bundle 并完成跨主机节点退出/恢复演练，或出现可验证的 Relay / DHT 需求与完整威胁模型时，应重新评估本决策。
